# Handoff: ask for notification permission after onboarding (IN-GR-034)

**Date:** 2026-09-17 · **Source:** Growth S5 device pass (Joe, iPhone and Android 2.5.0) · **Size:** S to M, JS-only, ships by OTA · **Decision:** Joe, 17 Sept

```
Context: Videx. Live RN/Expo 56 app in native/ (native/src/lib is a junction to the shared src/lib; never recursive-delete inside native/). Read first: native/src/notifications/push.ts (maybePromptForPush, enableNotifications, registerPushToken, clearPushToken, PROMPT_SHOWN_KEY), native/src/providers/notifications.tsx (silent register on sign-in when already granted; the header comment records the current "ask after value, not at launch" rule), native/src/components/WatchlistActions.tsx (the only caller of maybePromptForPush today), native/src/app/curating.tsx (end of onboarding: first_home_view, signup_completed, replace to For You, resume a pending shared link), native/src/components/profile/ProfileNotifications.tsx (explicit opt-in and the blocked → OS settings path), videx-wiki/wiki/concepts/architecture/notifications-v1.md (Consent section), docs/legal/privacy-policy.md and native/src/legal/policyContent.ts (check whether either describes when we ask), videx-wiki/AGENTS.md, and the memory note reference_ios_device_testing (Joe's iPhone takes ad-hoc builds only; JS fixes reach it by OTA via ota-update.yml, channel preview, platform ios; Android Play internal builds are on channel production with the same 2.5.0 fingerprint). Worktree branch off main named feat/notification-prompt-onboarding, relative paths. Expo docs: read https://docs.expo.dev/versions/v56.0.0/sdk/notifications/ before writing code.

Problem (Growth S5, IN-GR-034): on both platforms a new person is never asked for notification permission unless they add a title to their watchlist, and existing installs that never added one after install never see it. Testers had to find Profile → Notifications to turn alerts on. Arrival and leaving-soon pushes are the retention and G1 "Tell someone" loop, so a missing token means the loop never starts.

Decision (Joe, 17 Sept): ask when the person first lands, like most apps, replacing "first watchlist add". Placement agreed: after onboarding, on the first For You view, not at cold launch (no account yet to attach a token to, and an unexplained system prompt at launch is refused more often; on iOS a refusal is permanent until Settings).

Do:
1. A short in-app explainer before the system prompt (one sheet or card on For You, tone guide applies, no em dashes): what the alerts are ("Get told when something on your watchlist lands on your services, or is about to leave"), with "Turn on" and "Not now". "Turn on" calls the system prompt and registers the token on grant. "Not now" records the decline locally and never re-asks automatically (Profile → Notifications stays the way back in). Do not show it when permission is already granted (register silently instead) or permanently blocked.
2. Trigger once per install and account, after onboarding completes (curating.tsx → For You), and after any pending shared link has been shown, so the prompt never covers the shared title. Existing signed-in users who were never asked (PROMPT_SHOWN_KEY unset and permission undetermined) get the same explainer once on their next For You visit.
3. Keep maybePromptForPush's guarantees: at most one automatic ask per device, respect a permanent denial, and clearPushToken on sign-out still resets the key so the next account on a shared phone gets its own ask. Decide whether the watchlist-add trigger stays as a fallback (recommended: remove it, one entry point) and say which in the summary.
4. Android 13+: POST_NOTIFICATIONS is a runtime permission; confirm the Expo request covers it and that a denial on Android leaves canAskAgain behaviour correct.
5. Tests: unit-test the decision logic (granted, undetermined, blocked, already asked, declined, pending link present) as a pure function in src/lib or native/src with the existing vitest setup. Gates: native `npx tsc --noEmit` and `npm run lint` (root npm install first).
6. Docs: update the notifications-v1 wiki Consent section and the provider header comment (the rule changes from "first watchlist add" to "after onboarding with an explainer"); check the privacy policy and in-app mirror for any wording about when we ask, and if either changes, Joe approves the wording and policyContent.ts is re-mirrored. Add IN-GR-034 to videx-wiki/wiki/registers/parking-lot.md (closed with the PR), append videx-wiki/log.md.
7. One PR; merge is Joe's. Device check before merge via OTA (iOS preview channel; Android production channel reaches only Play internal testers on 2.5.0): delete and reinstall, sign up, finish onboarding, see the explainer on For You, Turn on → system prompt → a user_push_tokens row with app_version 2.5.0; repeat with Not now → no system prompt, no row, Profile → Notifications still turns it on; a shared-link sign-up shows the title first and the explainer after.

8. While in native/src/components/WatchlistActions.tsx (IN-GR-035, from the strategy-thread review of #197): the signed-out guard reads `session` but not `initializing` from useAuth, so a tap during session restore (a cold link open) bounces to /auth although a session exists. Disable both buttons while `initializing` is true (or treat initializing as signed-in for the guard and let the write wait); one line plus a comment. Close IN-GR-035 in the same PR.

Out of scope: push copy, send-notifications, notification types or preferences, any server change. Ordering note: Growth S5's fixes (PR #197) and the Apple button (IN-GR-032) are also OTA'd from branches; publish this OTA only after those have merged to main, or it will replace them on Joe's iPhone.
```
